# 招投标公告跨源去重

同一份招标公告会同时出现在多个平台上：省级公共资源交易中心、市级平台、行业垂直网站、代理机构官网、央企自建采购平台等等。

抓下来以后，正文里混着各家自己的导航和页脚，字段有的缺一半；公告本身短的时候，这些网站外壳反而占了大半篇幅。

人可以通过项目编号等信息判断是否同一条公告。但要让机器判断，则是另一回事：先是没有一个能直接用的判据，其次是数据量上来之后，准确率和计算成本之间需要进行权衡。

本项目解决这个问题。

> **核心实现未开源。** 本仓库公开的是问题定义、方法思路、评测口径与实测结果，不含实现代码。

## 一、难点

表面上看不难：标题一样的两条，比一比正文——一样就是重复，不一样就是不同的公告。

但是真正放到场景里就全是问题。

### 1. 常规思路的理论基础都是：文本像 ≈ 重复，也就是文本相似度

文本去重在工业界有一整套成熟方法。逐个看它们的原理、适用场景，再看为什么在这个场景下不可行。

#### 精确摘要（MD5 / SHA）

- **原理**：对整篇正文做哈希，摘要一致即字节级完全一致。
- **适用**：镜像站、同源转载、版本比对——内容一字未改的场景。判定零误判，成本可以忽略。
- **问题**：跨源发布必然经过重新排版，空格、换行、HTML 结构、日期格式都可能不同。差一个字节，摘要就完全不同。它能抓的只有"完全一样"，而我们要抓的是"是同一条、但表现形式不同"。

#### 编辑距离（Levenshtein / Jaro-Winkler）

- **原理**：把 A 串改成 B 串所需的最少增删改次数；Jaro-Winkler 额外给相同前缀更高的权重。
- **适用**：短文本和字段级比对——公司名、人名、地址的模糊匹配，拼写纠错的候选排序。文本越短越可靠，这类工具是首选。
- **问题**：单次计算是 O(n·m)，两篇几千字的公告就是百万级操作，比一次指纹比对贵好几个数量级。而且它对篇幅和顺序极其敏感——短公告被网站外壳包住之后，距离值基本由外壳决定。

#### n-gram 集合 + Jaccard / MinHash / LSH

- **原理**：把文本切成 k 个连续字符（或词）的集合，用交集与并集之比衡量重合度；MinHash 把集合压成固定长度的签名，LSH 再按签名分桶，从而避免两两比对。
- **适用**：网页去重的经典路线（Broder 的 shingling 方案，AltaVista 时代就在用）。成熟、可分布式，是海量文本近邻检索的工程标准。
- **问题**：它仍然落在全文级"重合度"这个维度上。网站外壳的文字一样进集合、一样贡献重合度；而短公告切出来的 k-gram 数量太少，Jaccard 方差很大，结果极不稳定。

#### TF-IDF / BM25 + 余弦相似度

- **原理**：把文档变成词项权重向量（词频 × 逆文档频率，BM25 再做长度归一与饱和），用向量夹角衡量相似。IDF 的作用是压低"到处都有的词"、抬高"少见的词"。
- **适用**：检索排序、长文档主题相似度，搜索引擎的默认基座。比对本身是两个稀疏向量的点积，很快，开销在分词和向量化。
- **问题**：作用在全文上时，一个词的权重由"它在这个语料里稀不稀有"决定，而不是由"它能不能区分公告"决定。模板套话和外壳文字在语料里确实常见、权重会被压低，但它们占据了绝大部分篇幅——向量终究是被它们拉过去的。

#### SimHash

- **原理**：把每个特征哈希成定长（常见 64 位），逐位加权投票——出现越多的特征票越重——得到整篇的指纹；两篇指纹的汉明距离小即相似。
- **适用**：海量网页的近似去重。存储 O(1)，比对只需一次异或加 popcount，天生适配亿级规模，且容忍正文有少量增删。
- **问题**：它押注"文本像 ≈ 重复"，而招投标公告两个方向都不成立。更要命的是逐位投票意味着**票数由篇幅决定**——模板和外壳字数最多、票最多，真正决定"是哪个项目"的编号字数最少、票最少。
- **实测**：这正是最早选用的方案，准确率在 50% 左右，很难再提上去。

#### 语义向量（BERT / 双塔 / Sentence-BERT + 近似近邻索引）

- **原理**：用预训练模型把文本编码成稠密向量，语义越近余弦越高；配合 HNSW / IVF 这类近似近邻索引，可以绕开两两比对。
- **适用**：语义检索、问答、需要理解同义改写的场景。"说法不同、意思一样"是它的强项，也是前面几种方法都做不到的。
- **问题**：它的训练目标是"语义相似"，而我们要的是"是不是同一个项目"，这两个目标在这批数据上恰好背离。同模板的一批公告语义高度相似（都是办公用品采购）；短公告被外壳主导后，语义也确实不同（外壳是网站介绍和相关推荐）。**它不是输出有噪声，而是系统性地朝错误方向输出**——换更强的模型，只会更自信地给出同一个错。
- **成本**：编码与向量存储的开销随数据量线性上升，在本项目的量级上同样不可接受。这也是很多平台止步于"同源去重"或"当天去重"的原因。

#### 记录链接 / 实体对齐（blocking + 字段级匹配）

- **原理**：上面几种把整篇当成一个整体来比，这一类把它拆开——先用一个强键（blocking key）把记录分桶，把两两比对降成桶内比对；再在桶内逐字段比对，每个字段算一个相似度，按证据强度加权后判决。工业界的名字是 record linkage / entity resolution，较早的系统化方法出自 Fellegi 与 Sunter 1969 年为人口普查做的匹配模型。
- **适用**：没有全局唯一主键、只有若干各自会错会缺的字段，却要判断"是不是同一个实体"的场景——客户主数据合并、商品去重、跨系统用户对齐。**它回答的正是我们要问的问题。**
- **在这里：方向对，经典做法用不了。** 它是唯一一个问对了问题的方向，但标准形态要求字段已经干净地躺在表里——提取是别人的事，甚至默认它不会错。而这里的输入是上百个源各自排版的网页，提取本身就是最不确定的一环。经典方法把最脏的这一步划在了自己范围之外，本项目躲不开。
- **所以要解决的，是怎么对冲提取误差**。

#### 小结

前六种都在回答"这两篇像不像"，只有第七种在回答"这两条是不是同一个"。

从本质上说，是对问题的定义不同：**要做的是实体对齐，不是相似度计算。** 而任何落在全文上的"像不像"，都必然把篇幅最大的部分当成最重要的部分——公告里篇幅最大的部分，恰恰是模板和网站外壳。

### 2. 两个截然相反的问题

SimHash 本来最适合这个数据量级——把整篇压成一个指纹，快速判断有没有重复。但它在这类数据上不可靠，而且会在两个截然相反的方向上都遇到问题。

**一个方向是模板化公告。**

这类公告大篇幅一模一样，采购单位、代理机构、条款措辞全都一样，但确实是不同的招标公告。文本像，不是重复。

同一项目不同阶段的公告也属于这一类。招标公告 → 变更/澄清 → 中标候选人公示 → 中标结果公告 → 合同公告，这些在业务上是不同记录，但正文高度重合，变更公告的正文常常就是原公告全文加一段说明。

**另一个方向更麻烦，是短公告。**

有的公告内容很少，这时候网站自己的东西——导航、介绍、广告——反而占了大半篇幅。两个网站的外壳不一样，内文其实是同一条，但整体看差异很大。文本不像，是同一条。

这两个方向的错法相反，中间没有单调关系：阈值调严，短公告全漏；调松，模板公告全错。无论怎么扫阈值，总有一头在塌。

问题不出在相似度算得准不准，而在于**信号被篇幅淹没了**。公告的长短不受我们控制，外壳占多大比例也不受我们控制。

### 3. 精确特征比对

不比文本了，直接提特征比——也就是前面那一条"记录链接 / 实体对齐"。项目编号、采购单位这些，重复的话应该对得上。

但是同样会遇上一个绕不过去的问题：

提取本身有准确率上限。不管用什么方法，抠出来的编号总有抠错的、抠漏的，做不到百分之百。而且**还有的公告压根没有项目编号**。

于是想到多加几个字段，公司名、金额都放进来，没编号的用别的补。

但是每个字段都有各自的错误率，字段一多，综合正确率是往下掉的，不是往上走的。**加字段是用错误率换区分度，字段越多越亏。**

最后使用一堆本身就存在错误率的字段去判重，准确性难以保证。

### 4. 所以难在哪

两条路都不通。

文本相似度便宜，但数据本身的性质决定了它两个方向都会错。结构化特征方向对，但提取环节决定了它覆盖不全，而且加字段只会更糟。

两条路还都得先满足成本约束——不只是比对次数，还有单次比对本身的耗时。

三个约束的方向是相反的：

- 要压成本，就得把参与比对的内容收窄
- 收窄到标识性内容，模板化公告之间就分不开了
- 想加字段把区分度补回来，误差又会累积

**没有免费的落点**——往哪边挪都会塌。这也解释了为什么"换个更强的语义模型"不是解法：模型强弱改变不了信噪比，也改变不了提取误差。

## 三、效果

### 数据规模

| 项 | 值 |
|---|---|
| 公告条数 | 36,000 |
| 来源数 | 120 |
| 唯一标题数 | 8,965 |
| 数据性质 | 公开渠道发布的招标采购公告 |

判定对象是**标题相同的两条公告**。

样本为 **1000 对人工标注**（432 对真重复 / 535 对非重复），均为标题相同的配对。其中 33 对因页面内容为空无法参与判定，不计入指标（可评 967 对）。

| 指标 | 数值 |
|---|---|
| 召回率 | 91.8% |
| 精确率 | 90.6% |
| F1 | 0.912 |

## 四、已知边界

- **泛化标题大桶**：102 个桶大小 ≥ 20，前 50 个桶贡献了 69.7% 的比对量，需要在桶内做二次分桶
- **链式误合并**：判定是逐对做的，合并成组时若按连通分量做传递闭包，A≈B、B≈C 会把 A 和 C 并进同一组，即使这两条毫无关系。桶越大链越长，风险越高——泛化标题大桶正是高危区
- **无标识内容的公告**：正文里若不含任何标识性内容，缺少可用的匹配依据
- **桶外内容不会被比较**：分桶键的选择直接决定召回上限
- **评测样本规模有限**：967 对可评样本足以说明量级，更细的差异不宜过度解读

## 六、在线试用

部署了一个**单对判定**接口，可以直接调用看效果。

```
POST http://123.57.204.194:9099/deplicate
Content-Type: application/json
```

### 入参

请求体为 JSON，两个字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `data1` | object | 是 | 第一条公告 |
| `data1.page` | string | 是 | 公告 HTML 全文，UTF-8 |
| `data2` | object | 是 | 第二条公告 |
| `data2.page` | string | 是 | 同上 |

`page` 直接传抓下来的原始 HTML 即可——带 `<html>`/`<body>`、带导航页脚都没关系，服务端会自行剥离标签。传纯文本也可以。

```bash
curl -X POST http://123.57.204.194:9099/deplicate \
  -H "Content-Type: application/json" \
  -d '{"data1":{"page":"<html><body>Project No: 21A00222, Amount: 30000</body></html>"},"data2":{"page":"<html><body>Project No: 21A00222, Amount: 30000</body></html>"}}'
```

> **正文含中文时**，Windows 终端用 `-d` 直接传参会破坏 UTF-8 编码，返回 400。
> 改为写入文件再传：
>
> ```bash
> cat > payload.json <<'EOF'
> {"data1":{"page":"<html><body>项目编号：21A00222 中标金额：30000元</body></html>"},
>  "data2":{"page":"<html><body>项目编号：21A00222 中标金额：30000元</body></html>"}}
> EOF
>
> curl -X POST http://123.57.204.194:9099/deplicate \
>   -H "Content-Type: application/json" --data-binary @payload.json
> ```

### 出参

**成功**（HTTP 200）

```json
{"result": true}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `result` | boolean | `true` 判定为重复，`false` 判定为不重复 |

**失败**（HTTP 4xx）

```json
{"error": "invalid request"}
```

| 状态码 | `error` 值 | 含义 |
|---|---|---|
| 400 | `invalid request` | 不是合法 JSON，或字段缺失 / 类型不对 |
| 401 | `unauthorized` | 令牌错误（默认未启用） |
| 413 | `payload too large` | 超过 512 KB（压缩前后同一上限） |
| 415 | `unsupported content-encoding` | 不支持的压缩方式 |
| 429 | `rate limit exceeded` | 触发限流，响应头带 `Retry-After: 1` |

### 支持 gzip

请求体大于 30 KB 时建议压缩，实测端到端快 30% 左右：

```python
import gzip, json, urllib.request

payload = {"data1": {"page": html1}, "data2": {"page": html2}}
body = gzip.compress(json.dumps(payload, ensure_ascii=False).encode())

req = urllib.request.Request(
    "http://123.57.204.194:9099/deplicate",
    data=body,
    headers={
        "Content-Type": "application/json",
        "Content-Encoding": "gzip",
    },
)
```

不压缩时行为完全不变——`Content-Encoding` 头留空即可。

> Python 客户端建议用 `ensure_ascii=False`，中文不转义成 `\uXXXX`，体积再小 6%。

### 限制

| 项 | 限制 | 超出时 |
|---|---|---|
| 单 IP | 20 次/秒，突发 40 次 | `429` |
| 全局 | 300 次/秒 | `429` |
| 请求体 | 512 KB（压缩前后同一上限） | `413` |

### 说明

这个接口**只做单对判定**——不含数据存储、不含分桶预筛，也不处理除了判重以外的任何环节。它的作用是让你用自己手上的数据快速验证判定效果，不是可直接上生产的产品形态。
